# 独夫：招式识别方案（计划，2026-10-24）

顺序 1–4 已完成，关 0、关 1 通过（关 1 按 2026-10-24 改后的口径），见文末「进展」。现状和试过的方向见 [dufu.md](dufu.md)。

## 为什么换

- 阶段二卡在约 10 挨打/分、存活约 2.5 分钟、boss 剩约 70%；调参和换 head 的 A/B 一直在误差内。
- 实战两三下就死，6 瓶药也只扛十几下，要接近无伤（约 10 倍改进），调参给不了。
- 感知：back9 把 840×530 缩到 96×96（8.75 倍），中距离 boss 只有十几个像素，起手和金红光纹理都糊了；阶段二又冻结了阶段一的 back9。
- 建模：只预测「几帧后有接触」，不知道 boss 出的是哪一招。挨打里 35% 是「时机对了、招本身没接住」，43% 是金光开场那一串，不认招解决不了。

## 目标

演练场接近无伤（≤ 1.5 挨打/分，连续 16 轮），再上实战。实战门槛要先量实战每下伤害是演练场的几倍。

## 核心思路

- 以 boss 为中心裁剪着看，不再整屏压成 96×96。
- 认出是哪一招，照这一招的时间表落指。
- 颜色定动作（红光卸势、金光闪避，老师定的），招式定时间（第几帧按）。
- 兜底都在新模型里：认不出招时用同一模型的通用头（光的颜色 + 接触时间）；颜色也拿不准就闪。不依赖旧的 `dufu.js`。

## 运行时（Pad，每帧约 10 ms 内）

```
抓屏 → ① 全局流（整屏低分辨率：大范围光效、距离）
     → ② 裁剪流（boss 区域：起手动作细节）
     → ③ 时序模型
          · 招式头：哪一招、起手后第几帧、置信度
          · 通用头：光的颜色、接触时间
     → ④ 决策层（招式表 + 动作原语：卸 / 闪 / 处决 / 喝药）
```

- 裁剪先用固定的中心双框（锁定后 boss 基本在画面中间：大框 530 → 192 管贴脸和大招，小框 260 → 192 管中远距离的起手）；录像统计证明有必要再加学出来的定位。
- 招式表每局之后自动修正：每招的提前量、能不能卸。

## 模型

- 每个 boss、每个阶段单独一个模型，不共享骨干网络；新模型从上一个训好的权重起步，全部重训，不冻结。
- 实战开局两个阶段的模型都加载，看到阶段信号就切换，阶段一快结束时阶段二的模型先在后台热起来。

## 招式分类：全自动

- 自动切片：接触、挨打、卸势成功事件加运动量，找起手帧。
- 自动聚类：类别数自动定，招式只有编号，不起名字。很多招起手一样、后面才分叉，所以招式按「到当前这一下为止」认（前缀）：分不开的类在分叉前合成一组，每一下重新认一次。
- 自动检查：同类里接触节奏分两拨就拆；两类节奏和应对一样就并；同类里金红混在一起，按颜色拆。
- 新招先归「未知」，由通用头处理，攒够了自动成新类。
- 好不好看实战结果（这一类卸 / 闪的成功率），不看人工标签。
- 网页上可以随时看各类样例和成功率，拆、并、改颜色，下次重训生效；没人看，流程照跑。

## 训练（PC，5080）

自动切片 → 自动聚类 → 大模型（老师）→ 蒸馏成小模型（学生）→ 量化 → PC 和 Pad 逐帧对拍。全程无人值守。

## 自动闭环

```
无人跑局（演练场）→ 入库 → 自动切片和聚类 → 重训 → 离线关卡
→ 影子模式上机 → 擂台（新旧模型 8 对 8 交替）→ 更好就升级，否则丢弃 → 回到跑局
```

- 人工纠错只是输入，不是一步。
- 每天自动出报告：各类成功率、升级 / 丢弃记录、异常。
- 无人值守要处理：游戏闪退 / 卡加载重进，Shizuku 掉了重启，过热暂停，存储低暂停，连续失败熔断后通知。录像拉到 PC 后从 Pad 删掉。

## NPU：MaaLow 的可选插件

- QNN 运行时和高通的库单独打包、单独发版，不进主 App，不碰 MaaFramework 自带的 onnxruntime。
- 没装：`infer()` 走 CPU。装了：多一个 `qnn` 选项，skill 写法不变。
- 训练流水线同时出 CPU 版和 QNN 版模型，用哪份看设备上有没有插件。
- 接通顺序：先试现有的 `nnapi` → Qualcomm AI Hub 云端真机测耗时（已同意上传模型权重）→ 做插件。走不通就用 CPU，模型小一号。

## 分层（以后接别的 boss）

## 进展

### 2026-10-24 顺序 1：数据底座 + 关 0 + NNAPI / AI Hub

脚本和细节在 [tools/dufu_moveid/README.md](../tools/dufu_moveid/README.md)，数据在 `data/moveid/`（git 忽略）。

**数据底座**：data/p2 的 197 轮录像（29.35 GB，p2b 的 57 轮都包含在内）全部拉到 PC，大小、头中尾字节、逐帧解码帧数都和 Pad 一致，然后从 Pad 删掉（Pad 上只剩 5 个不属于任何轮次的录像）。对时：录像帧 = k + t/33.33 + 每轮常数偏移（中位 −3.7 帧，r054 −17.4、r049 −7.9 两轮用血量 / 真气序列互相关复核过）。在每个有 hit 的轮次（195 轮）里，「|残差| ≤1 帧的 hit 占 ≥75%」都成立；按接触算，hit 97.1%、ok 99.0% 的 |残差| ≤1 帧。事件 7982 个（ok 3519、掉血 3354、金光 649、抓取后续 460），决策时刻 = 接触 − 10 帧。顺带发现：用 dufu.js 同款的血条 / 真气读法后，99% 的 ok 和 trace 时间对得上，dufu_train/README「约 30% 的 ok 早 6–12 帧」应是 check_align.py 的简化读法造成的。

**关 0：通过，走降级路线（全局流 384×240 + 固定双框）**。boss 框：开放词汇检测器分不开 boss、我方和 boss 召出的红龙。改成手标 726 帧，再微调 yolo11l；独立抽查 60 帧对 42 帧，主要错在红龙，所以覆盖率以手标框为准（520 个决策帧，177 轮；boss 可见 441 个）。「够用」= boss 框 ≥90% 面积在框内，且缩放后 boss 高 ≥40 px。

| 方案（boss 可见的帧） | 手标框 | 检测框（7440 帧） |
|---|---|---|
| 固定双框，中心 (555, 320) | 353/441 = 80.0% | 84.1% |
| 学出来的定位：上一帧框跟踪 / 理想上限 | – / 401/441 = 90.9% | 86.2% / 91.7% |
| 整屏 384×240 | 398/441 = 90.2% | 90.8% |
| 整屏 384×240 + 固定双框 | 428/441 = 97.1% | 98.0% |

- 固定双框的失败主要是抓取、贴脸近景（boss 比 530 的框还大，47/88 帧）；这些帧在整屏缩图里反而清楚，两路互补。
- 约 15% 的决策帧里 boss 根本看不见（被我方挡住、红光 / 爆炸盖住、抓取出画）。这些帧怎么裁剪都没用，不算进关 0 的分母，留给关 1 判断画面信息够不够。
- 总负责人用 726 帧手标框另写口径复算：固定双框 80.2%，整屏 86.8%，两路并用 95.4%。这组样本特意多挑了红龙帧，整屏单路在 90% 上下，两路并用稳定过线。
- 决定：全局流用 384×240，裁剪流用固定双框（中心 555, 320），不做运行时定位，也就不依赖不准的 boss 检测器。老师模型要用 boss 框的话，先解决红龙误检。

**NNAPI / AI Hub**：
- **Pad 实测**（游戏在前台；onnxruntime 单线程 run p50；喂输入另要约 5 ms，截图上裁剪和缩放也要另算）：
  - 裁剪流 MobileNetV3-S 192²：fp32 5.9 ms，int8 2.2–3.4 ms；
  - 全局流 384×240：MobileNetV3-S int8 5.2 ms，0.5 宽 int8 3.4 ms；
  - 两路裁剪拼成 6 通道：int8 2.5 ms；
  - 时序头：GRU128×2 1.0 ms，TCN int8 0.3 ms；
  - 多线程基本不比单线程快。
- **nnapi 没用**：
  - fp32 慢 4–10 倍（全局流 122 ms）；
  - fp16 和 CPU 一样快，说明整图都回落到了 CPU；
  - int8 建 session 失败，GRU 运行时报 OP_FAILED；
  - 这台机器的 NNAPI 后面没有可用的加速器。
- **AI Hub**（只上传了模型 ONNX；Pad 的 SoC 还没确认，先用 Galaxy S24 / 骁龙 8 Gen 3 测）：
  - 裁剪流、全局流 0.2–0.45 ms，全部层都在 NPU 上；
  - GRU 在 NPU 上被展开成 30 步，比 CPU 还慢（3 ms），时序头要放 NPU 就用 TCN；
  - back9 的 int8 版因为 Erf 算子编译失败。
- **结论**：
  - 只用 CPU：全局 0.5 宽 int8 + 6 通道裁剪 int8 + TCN int8，约 6–7 ms 加预处理，刚好放得下，学生模型按 int8 训练；
  - NPU：整套 <1 ms，QNN 插件值得做；
  - 待办：确认 Pad 的 SoC（`/status` 加 `Build.SOC_MODEL`，顺序 4 装插件时一起做），用同芯片的设备重测。

### 2026-10-24 顺序 2：自动切片和聚类

**光色**：只看录像像素。先找候选，再用 ResNet-18 分类：先找水平亮线，切出小图，分成红光 / 金光 / 碰撞火花 / 其他四类。训练用的 478 张小图是手标的，标签和颜色都由脚本自动产出。

- **抽查**：金 60 个、红 60 个，金红互判 0 次；40 个和 aux flare 不一致的，复核下来 40 个都判对了。总负责人抽看了金、红、没光三张网格图，金红判定都对。
- **漏标**：「没光」里可能漏了少量很淡的红光，不影响金光误判成红光这一项。
- **分布**：7982 个接触中，金 554、红 523、没光 6827、unknown 78。
- **卸势成功率**（ok ÷ (ok + hit_pf)）：金 2.2%、红 89.3%、没光 71.3%，和「金光卸不了、红光能卸」一致。
- **光出现到接触**（中位）：金 10 帧、红 14 帧。金光大多在决策时刻（−10）前后才出现，关 1 要特别看这一点。

**连段**：相邻接触间隔 ≤73 帧（间隔分布的低谷），而且后一下没有新的光，就算同一招。共 3403 串：3246 次出招 + 157 次抓取。

- 开场金光 554、红光 523、没光 2323。
- 掉血：中位约 5%，95% 分位约 9–10%。

**特征**：

- **模型**：DINOv3 ViT-S+/16 的 CLS，三路视图（关 0 定的）逐帧抽，共 737,198 帧，1.7 GB。
- **重复帧**：约 12% 的帧是录像重复上一帧，抓屏没跟上，切片和训练都要当作「没有新画面」。
- **运动量**：峰值在接触后 +2 到 +3 帧，能标出接触，标不出起手。

**聚类**：一条命令无人值守跑完（`s2c_all.py`，约 3.5 分钟，结果可复现）。

- **类别数**：出招 42 类 + 抓取 1 类。
- **画面窗口只用到接触前 −11 帧**：把接触后的画面放进去，同一招会按「卸住 / 挨打」被拆开（接触后主要是火花或受击闪光）。接触后的信息只通过节奏进入。

| 验收项 | 结果 |
|---|---|
| 覆盖率（非抓取，不算「未知」） | 3094/3246 = 95.3%（复算一致） |
| 颜色纯度：每类少数方 | 全部 ≤3%，最差 0.7%（复算一致） |
| 串长众数占比 | 按串加权 0.90；31 类 ≥0.9，7 类 <0.7 |
| 第 2 个接触偏移的类内 IQR | 各类中位 5 帧，最大 28 帧 |
| 稳定性 ARI | 奇偶轮 0.67 / 0.65；换种子 0.86–0.93 |
| 致命招 | 22 类覆盖 81% 掉血（复算口径不同，为 20 类） |

**拼图**：

- **一致的**：大部分金光、红光类。c3 是贴脸金面重击，开场没有光，卸住率 0，一个没光却卸不了的例子，要靠招式表的「能不能卸」处理。
- **混了不同动作的**：c0 / c2 / c4 这些近身单发、二段类，c1 混了远处红龙喷火和近身。
- **同一招被拆开的**：红龙招因为镜头远近被拆成几类；c11 / c40 是同一套金光连段，只是少了一段。
- **疑似漏标的抓取**：c41。
- 拆开对应对影响不大（时间表相同）；混了不同动作的类留给闭环按实战成功率继续拆。

**带到关 1 的注意**：类别是用接触前 [−60, −11] 帧的画面定的，和老师模型决策时刻能看到的画面重叠，所以「决策时刻认出类号」的准确率有一部分是循环论证。关 1 除了按类报，还必须报不依赖聚类定义的指标：

- 开场颜色：金 / 红 / 没光，要求金招被当成红招 ≤3%；
- 下一次接触的时间误差；
- 致命类能不能卸，按实战结果。

### 2026-10-24 顺序 3：老师模型 → 关 1（按原口径未过，等决定）

**老师模型**：

- **结构**：三路视图逐帧的 DINOv3 S+/16 patch token（冻结），每帧 651 个 token，缓存 112 GB；每帧用注意力池化压成一组，再接 4 层因果 transformer，看决策前 32 帧。
- **输出**：招式类（45：43 类 + 未知 + 空闲）、开场颜色（3）、距下一次接触的帧数（47 档）。
- **训练**：按轮次 5 折，数字全部是 out-of-fold；训练 77 分钟。
- **对照**：DINOv3 CLS 的线性分类器和最近类中心。
- **判定口径**：训练前写定（`s3_gate1.py`）。

| −10 帧 | 老师 | CLS 线性 | 阈值 |
|---|---|---|---|
| (a) 金招判成红招 | 1/554 = 0.2% | 0.7% | ≤3% ✓ |
| (b) 致命类 top-1（应对等价组内的混淆不算错） | 1410/2150 = 65.6% | 65.3% | ≥90% ✗ |
| (c) 下一次接触时间误差，中位 / 90 分位 | 3 / 15 帧 | 5 / 14 帧 | – |
| (c) 致命串应对（闪 / 卸）判对 | 2089/2149 = 97.2% | 95.7% | – |
| 其中该闪判成卸 | 44/698 = 6.3% | 4.7% | – |

- **换帧也不过**：−8、−6 帧上 (b) 是 66.0%、65.5%；−16 到 −4 帧之间基本不动。
- **颜色**：金光判成「没光」从 −16 帧的 7.0% 降到 −4 帧的 2.2%。
- **总负责人复核**：用 `oof.npz` 另写代码复算 (a)、(b)，分子分母完全一致；错例图也看过。

**为什么 (b) 不过（证据）**：

1. **类别里含决策之后才发生的事**：聚类的类别把第 2–4 个接触的节奏算进去了。
   - c0（两段）和 c2（单发）从 −16 帧到 −4 帧画面是同一个起手，区别只在有没有第二下。
   - 同一批 ≥3 段的致命串，在第 1 / 2 / 3 个接触前 10 帧认类，准确率是 49% / 65% / 71%。
   - 在接触帧（0）上也只有 65.9%。
   - 换更大的模型解决不了这个问题。
2. **真实的信息缺口**：c27、c4 这两类，boss 在远处、出画或被我方挡住，到接触时才冲进画面。模型一直判「空闲」，这是「该闪判成卸」6.3% 的主要来源。
3. **标签问题**：c40 / c11（同一招少一段）、c41 / c42（漏标的抓取），顺序 2 已标出。

**解读**：决策要用的信息在画面里：颜色（金→红 0.2%）、应对（97%）、接触时间（中位误差 3 帧）。原口径的 (b) 衡量的是「决策时刻能不能预知整招的后续节奏」，这个问题本身问错了。但阈值和口径是方案定好的，要不要改由人定。

**待解决**：接触时间 90 分位误差 15 帧，而卸势窗口只有 3–9 帧。无论选哪条路，这都是关 2 的主要风险。
